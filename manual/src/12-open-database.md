## The open database {#ch-open-database}

::: {.dek}
A key in the browser is fine only if the database checks who is asking.
:::

### What happened

**Moltbook.** Moltbook was a social network for AI agents. It went viral in late January 2026. Its creator wrote: "I didn't write a single line of code for @moltbook" [[wiz-moltbook]]. Researchers at Wiz, a cloud security company, read the JavaScript that the site sent to every visitor. Inside it they found the key to Moltbook's Supabase database. Supabase is a popular hosted database service for web apps. With that key, anyone could read and change every table [[wiz-moltbook]].

Wiz counted what was exposed: "1.5 million API authentication tokens", "35,000 email addresses" and "4,060 private DM conversations between agents". The data also showed "only 17,000 human owners" behind the agents [[wiz-moltbook]]. Wiz contacted Moltbook on 31 January at 21:48 UTC. Moltbook secured the first tables within two hours, and secured every table by 01:00 UTC on 1 February [[wiz-moltbook]].

**Lovable.** Moltbook was not the first. On 20 March 2025, a researcher named Matt Palmer found that apps generated by Lovable, an AI app builder, let outsiders query their databases directly [[palmer-cve]]. In 1,645 Lovable apps he found "303 endpoints across 170 projects (approximately 10.3% of the 1645 analyzed)" that were open [[palmer-statement]]. The exposed data included names, email addresses, payment and subscription records, and other services' API keys [[palmer-cve]]. The flaw became CVE-2025-48757, published on 29 May 2025 [[palmer-cve; cve-48757]]. (A CVE is a public ID number for a known security flaw.)

**Escape's scan.** In October 2025 the security company Escape reported that it had scanned "over 5,600 publicly available applications" built on vibe-coding platforms, about 4,000 of them on Lovable [[escape-method]]. It found "more than 2,000 vulnerabilities", "400+ exposed secrets" and 175 cases of exposed personal data, including "medical records, IBANs", phone numbers and emails. All of it was "accessible directly through public endpoints" [[escape-method]]. Escape scanned without trying to break in, so it calls these numbers a lower bound.

### Why it happened, in plain words

::: {.box .plain-words}
**Plain words**

- **Supabase public key:** a key that Supabase apps are meant to put in the browser. On its own it is only an ID for your project.
- **Row-level security (RLS):** rules inside the database that decide, row by row, which visitor may read or change which data. "Row" means one record, such as one user's profile.
:::

Supabase apps talk to the database straight from the browser. That design is safe only when RLS rules check every request. Wiz explains that the public key "acts like a project identifier", but "without RLS policies, this key grants full database access to anyone who has it" [[wiz-moltbook]]. Moltbook had no RLS policies, so its public key worked like a master key.

The Lovable apps had the same problem: missing or weak RLS policies [[palmer-cve]]. Lovable later added a security scan. Palmer's view is that the scan "checks for the existence of any RLS policy, not its correctness" [[palmer-statement]]. A rule that exists is not the same as a rule that is right. A rule that says "any logged-in user may read every row" exists, and it still exposes everyone's data to anyone who signs up.

Escape adds one more reason: "Supabase's default security rules are permissive for development" [[escape-method]]. Settings that make building easy can stay switched on after launch.

Nobody had to be careless for this to happen. The AI tools produced apps that worked. They did not produce apps that refused strangers, and nobody tested that.

::: {.box .lesson}
**The lesson**

- Anything sent to the browser is public. Assume every visitor can read it.
- On Supabase, turn on RLS for every table and write a policy for each one. On Firebase, write security rules ({{ch:ch-doors}}).
- Test as a logged-out stranger, then as a second user: can account B see or change account A's data?
- These flaws are common. Assume your app has one until you have checked.
:::
